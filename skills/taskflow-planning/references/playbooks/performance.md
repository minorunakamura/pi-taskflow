# Performance Planning Playbook

計測できる性能問題の改善に使う。
`taskflow-planning` の共通手順に以下の観点を加える。承認・保存・Work Item 分割・終了は共通手順に戻る。

## 問題と基準値の計測

- 報告された遅延、throughput、メモリ使用量などの問題を、実際の workload で確認する。
- 何を測るかを明示し、単位、入力・データ量、環境、実行コマンド、反復回数、集計方法を揃えて現在の性能を計測する。warm-up や計測のばらつきが影響する場合は、その条件も記録する。
- 観測した基準値を記録する。計測できない場合は不足している条件と再開条件を報告し、推測した数値を baseline にしたり最終 Plan を確定したりしない。

## 原因調査と Probe

- 計測結果、profile、処理回数、I/O などの観測から bottleneck と考えられる原因を調べ、根拠と未確認の仮説を区別する。関連コード・呼び出し元・テストも共通手順で確認する。
- コードを読んだだけで最適化を選ばない。実験で検証すべき仮説があれば、共通手順の Probe で最小の実験を行い、観測結果から方針を判断する。Probe を本番実装や Work Item の完了にしない。
- 必要な計測・調査・Probe の結論から、原因に対応する最小の改善方針、維持する動作、対象外を決める。
- 目標や許容する trade-off がユーザー判断として未決定の場合だけ、Root で `grilling` と `ask_user_question` を使う。現在性能や原因など測れる事実をユーザーに判断させない。

## Plan に含める合格条件と再計測方法

- metric と単位、実測 baseline、workload・環境・反復・集計を含む計測方法、原因の根拠、必要なら Probe の結論、改善方針を含める。
- 「高速化する」ではなく、絶対値や baseline 比など計測可能な成功閾値を定義する。測定のばらつきを踏まえ、どの集計結果を閾値と比較するかも決める。
- 変更後に同じ条件・方法で再計測して baseline と成功閾値を比較する手順を定義する。動作を維持する回帰確認と関連する正式なチェックも含め、性能だけの成功で完了にしない。

実測 baseline、原因調査、成功閾値、検証方法が揃ったら、共通手順の設計・検証方法の確定に戻り、Root Agent が最終 Plan を作成して必須の `taskflow_plan_review` を受ける。
