# Bug Fix Planning Playbook

期待と異なる動作の修正に使う。`hotfix` も原則この Playbook を使い、緊急であっても診断と検証を省略しない。
`taskflow-planning` の共通手順に以下の観点を加える。承認・保存・Work Item 分割・終了は共通手順に戻る。

## 再現と原因確認

- 報告された問題の再現を試み、入力、環境、実行手順、期待する結果、実際の結果を記録する。
- 関連コード、処理の入口と流れ、呼び出し元、テストを確認し、原因の仮説と確認済みの事実を区別する。コード調査・外部調査・Probe は共通手順に従う。
- 再現結果、ログ、テスト、必要なら最小の Probe で、原因が観測された問題を説明することを確認する。コードを読んだだけの推測を確認済みの原因にしない。
- 再現できない、または原因が確認できない場合は、試した手順、得られた根拠、未確認点、再開に必要な条件を報告して調査を継続するか停止する。原因が未確認のまま、推測した修正を最終 Plan に確定して Plan Review に進まない。

## 修正方針

- 期待動作を既存の仕様・テストから確認する。仕様や方針が本当に未決定の場合だけ、Root で `grilling` と `ask_user_question` を使う。調査や実験で分かる事実をユーザーに判断させない。
- 原因の確認と必要なユーザー判断が済んでから、原因を直す最小の修正方針、影響する呼び出し元、維持する動作、対象外を決める。本番実装はまだ行わない。

## Plan に含める根拠と検証方法

- 再現条件と手順、期待・実際の結果、確認済みの原因とその根拠、修正方針を含める。
- 修正前に失敗し修正後に成功する回帰テストを定義する。適切なテストが作れない場合は、元の再現手順など実行可能な代替検証と期待結果を定義する。
- 維持する動作や関連する呼び出し元の回帰確認、正式なチェック、TDD の使用有無と使用する場合の公開インターフェースを決める。

必要な診断と判断が完了したら、共通手順の設計・検証方法の確定に戻り、Root Agent が最終 Plan を作成して必須の `taskflow_plan_review` を受ける。
