# Refactoring Planning Playbook

動作を変えない構造変更に使う。
`taskflow-planning` の共通手順に以下の観点を加える。承認・保存・Work Item 分割・終了は共通手順に戻る。

## 現在の動作と不変条件

- 目標構造を決める前に、現在の公開インターフェース、入力と出力、エラー、副作用、呼び出し元、関連テストと仕様を確認する。コード調査は共通手順に従う。
- 変えてはいけない動作を明示する。代表的な入力、境界条件、エラー条件で現在の結果を実行確認し、仕様上の期待と区別する。
- 動作を変更する必要が判明したら、Refactoring の範囲を黙って広げない。新しい動作・仕様変更は Feature、期待と異なる動作の修正は Bug Fix に再分類し、該当 Playbook で計画し直す。

## 目標構造

- 確認済みの現在動作と不変条件を前提に、変更対象、目標構造、維持する公開インターフェース、対象外を決める。
- 既存の構造や依存関係を使って目的を満たす最小の変更とする。将来用の抽象化や設定を加えず、本番実装はまだ行わない。
- 仕様・範囲・方針にユーザーしか決められない未決定事項がある場合だけ、共通手順の Root-level Grilling に戻る。

## Plan に含める等価性の検証方法

- 現在の動作、変えてはいけない動作、変更対象と目標構造を含める。
- 変更前後で同じ入力に対して出力・エラー・副作用が同じであることを確認するテストや実行手順、比較する結果、合格条件を定義する。現在のテストだけで不変条件を覆えない場合は、公開インターフェースを通した characterization test または実行可能な比較方法を決める。
- 関連する正式なチェックも決める。lint や typecheck の成功だけを動作の等価性の証明にしない。

不変条件、目標構造、等価性の検証方法が揃ったら、共通手順の設計・検証方法の確定に戻り、Root Agent が最終 Plan を作成して必須の `taskflow_plan_review` を受ける。
