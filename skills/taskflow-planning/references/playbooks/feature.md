# Feature Planning Playbook

新しい動作や既存の動作変更に使う。
`taskflow-planning` の共通手順に以下の観点を加える。承認・保存・Work Item 分割・終了は共通手順に戻る。

## 調査

- 変更対象の現在の動作、入口、公開インターフェース、処理の流れ、関連テストを確認する。
- 既存の公開 API、Skills、Extensions、Agents、依存関係で実現できる部分と、変更が必要な部分を区別する。
- 隣接する呼び出し元や利用者への影響、互換性、既存の設計・仕様の制約を確認する。
- 小さく明らかな依頼は Root Agent の直接確認でよい。それ以外のコード調査は built-in `scout` を使う。
- 外部仕様が必要なら `pi-ketch.researcher`、実験で確認できる不明点があれば Probe を共通手順に従って使う。

## 決定と設計

- 何を追加・変更するか、維持する動作、対象外を明確にする。
- 仕様、範囲、優先度、方針に未決定事項がある場合だけ、Root で `grilling` と `ask_user_question` を使う。
- 必要な調査、ユーザー判断、Probe の結論が揃ってから最小の実装方針を固める。本番実装はまだ行わない。
- 既存機能で足りるものを再実装せず、将来用の抽象化や設定を加えない。

## 完了条件と検証方法

- 新しい動作・変更された動作について、観測できる完了条件を決める。
- 維持する既存動作の回帰確認を含め、関連する正式なチェックと実際の操作・実行手順を決める。
- TDD の使用有無と、使用する場合の公開インターフェースを決める。テストが適さない場合は実行可能な代替確認を決める。
- 別の設計視点が有用な場合だけ built-in `oracle` に助言を求め、Root Agent が採否を判断する。

調査や判断が残っている場合は先に解決する。Root Agent が共通手順で最終 Plan を作成し、必須の `taskflow_plan_review`、Approved Plan の保存、`to-tickets` を進める。
Work Items がユーザー確認済みかつ保存・公開済みになったら終了し、Implementation へ続けない。
