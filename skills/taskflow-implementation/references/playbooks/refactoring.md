# Refactoring Implementation Playbook

動作を変えない構造変更に使う。
`taskflow-implementation` の共通手順を以下の観点で補う。Worker、正式なリポジトリチェック、独立した Correctness Review / Ponytail Review、指摘の採否・修正・再確認、Code Review gate、最終状態は共通手順に戻る。

## Worker 開始前に不変条件を確認する

- Work Item と Approved Plan から、目標構造、変更範囲、変えてはいけない動作、変更前後の比較方法と合格条件を特定する。
- 現在の公開インターフェース、呼び出し元、入力・出力・エラー・副作用を確認する。Plan の方法で変更前の動作を実行し、変更後と比較できる基準を確認する。
- 比較に characterization checks の追加が必要なら Plan に従い、構造変更前に現在の実装で成功する基準を確定させる。内部構造の一致を動作の等価性の代用にしない。

## 動作を維持して構造を変更する

- 共通の Worker 依頼に、不変条件、目標構造、変更前の確認結果、Plan の比較方法を含める。Worker は意図的に外部動作を変えず、承認済みの構造変更だけを行う。
- 動作・仕様変更が必要になった場合は Refactoring の範囲を広げず、`REPLAN_REQUIRED` として停止する。Worker 内で判明した場合も Root に戻し、別種別の実装をそのまま続けない。

## 変更前後の等価性を直接検証する

- Plan で定めた同じ入力・条件・方法で変更後を実行し、変更前の出力・エラー・副作用などの不変条件と比較する。Root が実際の結果を確認し、tests / lint / typecheck の成功だけで等価としない。
- 不一致があれば範囲内の回帰として共通の修正手順に戻り、影響した比較を再実行する。解消に動作・仕様変更が必要なら `REPLAN_REQUIRED`。
- 共通手順の正式チェックと両 Review を省略せず、変更前後の比較結果を渡す。等価性が確認できないまま成功扱いにしない。
