# Bug Fix Implementation Playbook

期待と異なる動作の修正に使う。`hotfix` でも再現・原因確認・直接検証を省略しない。
`taskflow-implementation` の共通手順を以下の観点で補う。Worker、正式なリポジトリチェック、独立した Correctness Review / Ponytail Review、指摘の採否・修正・再確認、Code Review gate、最終状態は共通手順に戻る。

## Worker 開始前に再現条件と原因を確認する

- Approved Plan の再現条件（入力・環境・手順）、期待結果と不具合の結果、診断済みの原因・根拠、修正方針、維持する動作を確認する。
- 現在のコードと呼び出し元を読み、元の再現手順を実行して、Plan の診断が現在の不具合を説明することを確認する。Planning の会話や Scout 出力で代用しない。
- 再現できない、原因の根拠が不足する場合は、観測結果と不足する条件を Root が整理し、確認できるまで実装を開始しない。原因や修正方針を実質的に変更する必要があれば `REPLAN_REQUIRED` として停止する。Worker 内で判明した場合も Root に戻す。

## 修正と TDD

- 共通の Worker 依頼に、確認した再現条件・原因・修正方針と回帰検証を含める。Plan に従って原因を直す最小の修正を行い、隣接する呼び出し元の動作を維持する。
- Approved Plan が明示的に TDD を指定した場合だけ、Matt Pocock の既存の `tdd` Skill を Worker に追加する（公開 `subagent` の `skill: "tdd"`）。承認済みの公開インターフェースを対象にする。
- TDD 指定がない場合は Skill を追加せず、Plan の回帰テストまたは実行可能な代替検証に従う。Bug Fix という種別だけを理由に TDD を選ばない。

## 元の再現手順で直接検証する

- 修正後に元の入力・環境・再現手順を再実行し、観測した不具合がなくなり期待結果になったことを Root が直接確認する。unit test の成功だけから修正済みと推測しない。
- Plan の回帰検証で維持する動作も確認し、修正前後の結果と未確認点を共通の両 Review に渡す。修正後の再確認でも元の再現手順を使う。
- 共通手順の正式チェックと両 Review を省略しない。直接確認できない、または不具合が残る場合は完了扱いにせず、停止理由と最終状態を共通手順で判断する。
