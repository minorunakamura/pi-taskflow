# Taskflow の検証資産連携・同時 Review・Work Item 粒度

## 目的と現在地

同じ基本設計から実装した旧・新の Taskflow 実行を比較した結果を受け、必要な保証を維持しながら検証の作り直し、Review 起動の手戻り、大きすぎる Work Item の確認負担を減らす。

2026-11-03 の Design Discussion で合意した方針を保存する。本書は Approved Plan や実装開始の許可ではない。Skill の改訂文面、実装手順、チケット分割・公開は後続の Planning で扱う。

## 範囲と前提

対象は、Planning / Implementation と再利用可能な検証 Skill の連携、Correctness / Ponytail Review の同時実行、Work Item 分割の判断基準である。

[既存の検証範囲・TDD 方針](planning-verification-policy.md)は維持する。保証対象・対象外、対象別の TDD 採否、Worker の focused regression、Root の正式チェックと直接検証、影響に応じた再検証を変更しない。既存テストの削除・移動、CI の頻度変更、既存 Approved Plan の書き換えは扱わない。

同文書の「新しい Skill を追加しない」は当時の TDD 方針整理の範囲での制約である。本書では、別途合意した拡張として独立した検証 Skill との連携を追加する。既存方針全体を置き換えず、新しい承認段階や Taskflow 専用の保存基盤も作らない。

## 1. 必要時に再実行できる検証資産

### 責務の分担

共通の Create / Maintain Skill は `pi-skills` で管理する。生成・保守するプロジェクト専用の検証 Skill、必要な補助スクリプト、Feature Map は検証対象のプロジェクトに置く。具体的な設計は[pi-skills 側の設計書](../../../pi-skills/docs/designs/reusable-verification.md)を参照する。この相対リンクは隣接 checkout 間の参照であり、実行時の固定配置を要求しない。

| 場面 | Taskflow の責務 |
| --- | --- |
| Planning | 既存の検証資産を確認し、不足があれば Create の必要性と対象範囲を Plan に含める。実際の生成・動作確認は行わない。 |
| Implementation | 適切な既存資産があれば再利用する。必要な資産がなければ Approved Plan の範囲で Create を実行し、生成した手順の成立と今回の完了条件を確認する。 |
| 関連機能の変更 | 今回関係する検証を実行し、必要な手順・スクリプト・Feature Map の関連部分を更新する。更新した検証方法も実行して確かめる。 |
| Map 全体の点検 | Maintain はユーザーが明示実行する。Taskflow から自動実行せず、通常の Implementation の必須工程にしない。 |

通常の関連部分の更新に Maintain を呼ぶ必要はない。Create も毎回の実行や全プロジェクトへの導入を要求しない。Skill の利用は、Root が保持する採否判断・直接検証・最終受入れの代行ではない。

### 既存の検証との境界

- 通常の自動テストと、Planning で不明な事実を確かめる使い捨ての探索実験は、既存の範囲・方針を維持する。
- 直接検証に使う再利用価値のある方法を保存する。探索実験や試行錯誤の全ファイルを保存すること、新しい検証プログラムを毎回作ることは要求しない。
- 資産を保存する判断と、CI や毎回の自動実行に含める判断を分ける。既存の正式チェックは省略しない。
- 保存した手順から今回の対象を選び、実際の入口と結果を確認する。過去の成功報告や証拠だけで変更後の成功を認定しない。
- 自動テストから除外した結合部分を、小さいテストで同等に保証したことにしない。保存する方式の変更だけで保証対象・完了条件を勝手に変えない。
- 必要な検証や資産作成に Plan の保証・設計の変更が必要なら、既存の確認・再計画経路を使う。

例えばリバーシでは、ルールの unit test を維持しながら、実 Worker、思考中の再開始、旧応答破棄、描画までの計測に使う手順の一部を再利用できる。これにより、別 Issue で同種の確認方法を最初から書き直す負担を減らす。ただし、今回も実行して確かめる費用と資産の保守費用は残る。

## 2. Correctness / Ponytail Review を同時実行する

動作確認後に、別々の fresh context の built-in `reviewer` を同時に動かす。単純化のための直列化や、一つの Reviewer への統合は行わない。

- Correctness Review：要求適合、不具合、回帰、テストと直接検証の不足、期待結果自体の要求との整合を確認する。
- Ponytail Review：この Reviewer だけに `ponytail-review` を指定し、不要な範囲・抽象化・既存機能の再実装などを確認する。
- 両者に、必要な正式入力、差分、Root の実行結果、直接検証の証拠と未確認範囲を渡す。既存どおり原則 read-only とする。
- Root は両方の結果を取得し、指摘の採否・修正・再検証を判断してから Code Review gate へ進む。起動失敗や結果未取得を「指摘なし」と扱わない。

独立した2回の非同期 `subagent` 呼び出しを使えば、子ごとの条件を分離して並行起動できる。named workflow の `parallel` を使うこと自体は必須にしない。workflow としてまとめる必要がある場合は、子ごとの条件に対応した公開の scripted workflow を使う。独自 wrapper や Agent 定義は追加しない。

### 確認したエラーと理由

新の実行では、named workflow の `parallel.args.tasks[]` と scripted workflow の `runs.all(...)` を混同した引数指定があった。

- Issue #1：`parallel.args.tasks[1]` の `skill` が unsupported fields として起動前に拒否された。
- Issue #2：同じく `parallel.args.tasks[0]` の `context` が拒否された。
- Issue #1 の修正過程では `workflow: true` と `options.script` を同時指定し、相互排他の入力検証にも失敗した。

確認時の named workflow の子項目は `agent` / `task` と任意の `cwd` / `model` を受け付け、子ごとの `skill` / `context` は受け付けない。Taskflow の役割要件をこの簡易形式へ無理に詰め込まない。具体的な呼び出しは導入済み `pi-subagents` の公開 Skill / guide に従う。

## 3. Work Item は小さく受け入れられる成果で分ける

「1セッションに収まりそうな最大量」ではなく、実装・検証・Review・人間の受入れまで扱いやすい小さい成果を基準にする。ユーザーから「大きいところを分割して」と指摘されてから見直すのではなく、最初の分割案を提示する前に Root が判断する。

- 独立して確認できる主要な振る舞いや、異なる検証・Review の対象をまとめすぎていないか。
- 途中に、動作を確認して一度受け入れる価値のある到達点がないか。
- 分割すると、本当に使い捨て実装、重複する編集、不自然な引継ぎが増えるか。
- まとめる場合は、その結合が必要な理由を示せるか。

既存の縦スライス（必要な層を貫く、動作を確認できる単位）、実際の blocker、正式 Plan の参照、分割・保存公開の承認は維持する。「層で分けない」を「全機能を一件にまとめる」と読み替えない。一方で、固定件数、行数、所要時間による一律の分割や、schema / API / UI / tests の層別分割は要求しない。

リバーシなら「人間の着手までの足場 → 浅い CPU で終局・再戦 → 応手探索と実測」は候補になる。2件・3件のいずれかを正解として固定せず、全体の進行効率と、人間が理解・確認する負担を比較する。中間成果で未実装の最終要件は明示し、製品全体の完了と混同しない。

## 根拠と受け入れるトレードオフ

- 旧 `pi-demo` と新 `pi-test/pi-test7` の `.pi/taskflow-reports/`、両者の `docs/plans/reversi.md` と関連ソースを比較した。入力の `docs/designs/reversi.md` は SHA-256 が一致した。
- 新は Worker 実行数と恒久テスト量が減った一方、直接検証の一時スクリプト作成・操作負担は Root に残った。保存・再利用を通常テストと使い捨ての中間に置く理由となった。
- 旧のユーザー2局の楽しさ確認と、新の Agent による1局の所見は同等ではない。時間短縮やテスト量削減だけを、同じ保証を維持した証明としない。本書はどちらかの対局数や確認主体を全プロジェクトの既定にするものではない。
- 同時 Review は独立性と待ち時間を維持しつつ API の混同を減らす。小さい Work Item は確認しやすい反面、引継ぎと受入れ回数が増えるため、単純に件数を増やすことを目標にしない。

## 後続で具体化すること・未検証事項

- `pi-skills` 側で共通 Skill の入口、生成物の配置・発見方法、証拠の保持方針を具体化してから、Taskflow との呼び出し契約を Planning で定める。連携先が未実装のため、現時点で特定のコマンドや固定パスを契約にしない。
- 独立した非同期 Review の指定が各 Reviewer に分離して渡ること、両結果を待ってから採否・Code Review に進むことは、改修後の実行で確認する。入力形式の照合だけを実動作確認の代わりにしない。
- 粒度判断は同程度の依頼で最初の分割案と検証・受入れ負担を観察する。今回一組の比較だけで、自律的な粒度判断や将来の時間短縮が保証されたとはしない。
- 本書は設計の引継ぎであり、既存の Plan / Work Item、Skill、本体コード、設定、承認状態は変更しない。
